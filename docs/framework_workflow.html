API Automation Robot Framework

Architecture, request lifecycle, validations, and report generation for the API test automation repository.

End-to-end workflow

Robot Framework loads a suite and its resources, reads each test-data row, builds an authenticated API request, validates the response, and writes execution artifacts.

Authentication-to-end-to-end execution

  1. Robot starts the selected suite. The command-line test path selects a suite such as tests\Regression Suite\channel_based_product_filteration.robot. Robot parses its Settings and loads imported libraries, Python helpers, and resource files before executing the test case.
  2. Variables and test data are resolved. resources\variables\api_variables.robot provides the product API base URL, endpoint, and CSV path. The suite calls Read Csv, implemented in python\csv_reader.py, and gets a list of dictionaries—one per data row.
  3. The suite passes a row into the API keyword. The product suite reads related party, depth, product code, category, and channel. The compatibility suite reads correlation group, SKU list, channel, and brand. Each suite loops through its rows.
  4. The keyword clears proxy settings and requests an access token. resources\keywords\api_keywords.robot invokes Get Access Token from resources\auth\auth_keywords.robot. That keyword reads IAM configuration from resources\auth\auth_variables.robot, prepares the form-encoded token request, and sends it to the configured IAM token endpoint.
  5. The IAM response is checked. The auth keyword expects HTTP 200, parses the JSON response, requires an access_token, and verifies it is not empty. If authentication fails or the expected token is absent, keyword execution stops and the test row is reported as failed.
  6. The API request is assembled and sent. For product offerings, the keyword prepares the query parameters and sends a GET to the product-offering endpoint. For compatibility, it constructs a cart-item JSON body and sends a POST. Both use RequestsLibrary and expect any HTTP result initially so the custom checks can report status failures clearly.
  7. The response is validated against the test row. The suite checks status/body/time/header, then calls Python validation keywords for response shape and business rules. Product-row failures are caught and accumulated so remaining CSV rows can still run; after the loop, any accumulated failures fail the overall Robot test.
  8. Robot writes run artifacts. On completion, Robot writes output.xml, log.html, and report.html to the selected output directory. The XML records keyword execution and statuses; the HTML files present the run in browser-readable form.
  9. Optional post-processing creates a Word report. python\generate_docx_report.py reads the Robot XML and builds a DOCX summary. This is a separate command and is not automatically run by Robot itself.

Authentication implementation note: the live API keywords request a token before each API operation. The standalone tests\Regression Suite\test_auth.robot is only a basic placeholder test that returns a sample token; it does not exercise the live IAM request flow.

Product-offering suite validations

For each row in product_offering.csv, the suite sends relatedParty.name, depth, code, category.name, and channel.name as query parameters.

  • HTTP status must be 200; response body must be non-empty; response time must be at most 5000 ms; content type must be JSON.
  • Offering schema and lifecycle status are checked; returned code, related party, and category are compared with the CSV row.
  • The root offering is expected to have type GroupProductOffering; nested records are traversed for simple offerings and prices.
  • For each populated channel list, the requested channel must be present. Other channel names may also be present. Empty or null lists are skipped by the channel validator; malformed values fail.
  • The validity helper parses provided dates but currently does not enforce the current validity window.

Scope note: A CSV row whose code resolves directly to a root SimpleProductOffering does not meet the current root-type expectation. The channel validator is a membership check, not strict filtering.

Compatibility-check suite

The compatibility suite reads correlation group, SKU list, channel, and brand from CSV; posts a JSON cart request; validates status, response body, required response fields, and echoed correlation/SKU values. If the compatibility result is false, it retries up to three attempts and fails if it remains false.

Running and locating reports

Run one API suite

python -m robot --outputdir reports\channel_based_product_filteration "tests\Regression Suite\channel_based_product_filteration.robot"

Run the parallel test runner

.\.venv\Scripts\python.exe run_parallel_tests.py

Generate a DOCX from Robot XML

.\.venv\Scripts\python.exe python\generate_docx_report.py reports\channel_based_product_filteration\output.xml reports\channel_based_product_filteration\Product_Offering_Test_Report.docx

Robot outputs include output.xml, log.html, and report.html inside the chosen output directory. The DOCX is generated separately from the XML.

Configuration and safe handling

Install dependencies from requirements.txt into the project virtual environment. Authentication values must be treated as secrets: do not include credentials or access tokens in reports, source control, screenshots, or shared documents. Prefer environment variables or a protected secret store for credentials.

The requirements manifest lists browser, database, and AI libraries in addition to API libraries. The workflows described here focus on the API suites and utilities actually present in the repository.
